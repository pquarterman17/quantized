# Frozen workspace (.dwk) fixtures — P1.2 box 2/3

`v1.dwk.json` / `v2.dwk.json` / `v3.dwk.json` / `v4.dwk.json` are **frozen**
documents, one per `.dwk` version this repo has ever shipped (see
`lib/workspace.ts`'s `WORKSPACE_VERSION` version-notes comment for what each
version bump added). They exist to give `lib/workspaceMigration.test.ts` a
real, honest fixture for migration and torn-write testing instead of an
inline object built by hand inside the test file.

**These files must never be hand-edited, and must never be silently
regenerated by re-running the serializer.** If a change to `parseWorkspace`,
`serializeWorkspace`, or the workbook-migration logic makes one of these
fixtures fail a test, that failure is a **migration-compatibility decision**
that needs a human to look at it — never a reason to just re-freeze the
fixture and make the red go away. (Same discipline as `tests/golden/` on the
backend side — see the root `CLAUDE.md`'s "golden-parity porting" notes.)

## Provenance

All four were derived from ONE real call to `serializeWorkspace` (never
typed out by hand) against a small but non-trivial `WorkspaceState`: 2
datasets ("run-a.csv" in a folder + workbook, "run-b.xy" at the Library
root in its own workbook), one folder, one pipeline step, one recalc mode
override, one saved Quick Plot template, one plot recipe (via
`captureRecipe`), and one editable figure (via `createFigureDocument`).

- `v4.dwk.json` is that real output verbatim (with `savedAt` pinned to a
  fixed timestamp instead of the call's real one, so the file is stable).
- `v3.dwk.json` is the v4 document with the workbook layer removed —
  `workbooks` deleted, `workbookId` deleted from every dataset — matching
  `workspace.ts`'s own version notes: v3 has the typed pipeline
  (`pipeline`/`recalcMode`) plus every field added later "additive-optional,
  no bump needed" (quick-plot templates, plot recipes, editable figures,
  smart folders, …); workbooks were the v3->v4 bump.
- `v2.dwk.json` keeps only what the version notes say v2 introduced over
  v1 — the folder tree (`folders`, dataset `folderId`) plus
  `activeId`/`selectedIds`/`expandedFolders`. No pipeline, no recipes, no
  workbooks.
- `v1.dwk.json` is datasets only — no `folderId`, no `workbookId`.

The generator script itself (`_generate.test.ts`, a one-off vitest file that
called the real `serializeWorkspace`/`captureRecipe`/`createFigureDocument`
and wrote these four files, then downgraded v4's own JSON object field-by-
field for v3/v2/v1 exactly as described above) was deleted after producing
these files — it was a tool, not a thing to keep re-running. If the fixture
set ever needs to grow (a new version, or richer content), rebuild it the
same honest way: construct a real `WorkspaceState`, call the real
`serializeWorkspace`, and derive older versions by deleting exactly the
fields that version notes say did not exist yet — never by hand-typing a
`.dwk` document from scratch.

## A known, deliberate non-determinism

`lib/pipeline.ts`'s `sanitizeSteps` mints a **fresh** id for every pipeline
step on every parse (its own docstring: "persisted ids could collide with
this session's counter") — so a workspace containing a pipeline step is
never byte-for-byte idempotent across two parse/serialize cycles on that one
field, by design, not a bug. `workspaceMigration.test.ts`'s idempotency
check normalizes `savedAt` (always a fresh timestamp) and each pipeline
step's `id` before comparing for exactly this reason; everything else must
match exactly.
