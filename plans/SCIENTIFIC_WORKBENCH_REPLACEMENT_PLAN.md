### Verified manual recalculation after reload

The reloaded graph's operation lock could still Go to Source. That command activated Book1/Sheet1 and selected the original 1,100 Y values. I changed the first Y from 0 to 9 in the reopened scratch project. The lock turned yellow, and the graph still showed the old fit. Recalculate was now enabled. Clicking it returned the lock to green and updated the fit curve and the on-graph table in place. The displayed intercept changed from 0.01557 to 0.04825, and the slope from −2.35947×10⁻⁵ to −6.81822×10⁻⁵. An independent ordinary least squares update for a +9 change at X=0 with X=0…1099 predicted intercept 0.0482527 and slope −6.81823×10⁻⁵ from the displayed baseline. Both agree within display rounding.

Add an explicit P0 regression to the result acceptance plan. Reopen a project, navigate from the result to the original input, edit one cell, verify the visible pending state and unchanged last result, then recalculate. Assert that the curve and on-graph table agree with an independent calculation. Cover Auto separately, including what happens to selection and the previous valid result when automatic computation fails. The post-reload source edit was intentionally left unsaved, so the downloadable scratch project is the pre-edit baseline.

## Implementation plan for replacing OriginPro and JMP

**Objective.** Quantized becomes the software used to finish the lab's plotting, data preparation, analysis, and reporting work currently done in OriginPro or JMP. A required workflow is ready when someone can start from the original inputs, find and run the right tools, reproduce the scientific result, reopen the saved project, and deliver the required output with both incumbent applications closed. Legacy files, recipes, or scripts belong in this test when they are needed for ongoing work. Keep catalog items visible so future needs can be evaluated. The breadth of the vendor catalogs is a source of test cases and candidate work. ## Product design plan for a first-class scientific workbench

Quantized should make a scientist's next step obvious and the scientific consequences inspectable. A user coming from OriginPro should be able to move fluidly between source data, figure and analysis. ### Interaction and visual rules to test

1. **Give context a visible home.** In views where Library selection, focused plot and analysis input can differ, identify the relevant object near each consequential action. Keep labels such as “Data · Wafer run 2 · pinned,” “Fit input · 21 of 24 rows,” and “Export figure · Thickness by wafer” visible before a command runs. For exclusions and row ranges, show both the scope and a route back to the underlying rows. Use existing stable identities. Duplicate-named datasets must still be distinguishable.
2. **Use the same verbs in every destination.** Select, Open, Edit, Run, Save result, Open as worksheet, Export and Send to report have different effects. Choose one term per effect, explain where outputs will go, and reflect existing availability in all routes. Keep tooltips for shortcuts or secondary details. A tooltip should be supplementary when a disabled action needs recovery. If a result is created in the background, acknowledge the named output and offer Show without changing the user's focus.
3. **Make common tasks short and advanced tools easy to reach.** Keep common methods and actions in visible menus. Offer keyboard accelerators, aliases and context actions as faster routes. Keep the model, data binding and critical scope visible in the workbench. Collapse advanced sections around the workflow, and remember local disclosure state where it helps repeated users. When a method has an important scientific assumption, put concise guidance beside the applicable setting and link out to the full method details.
4. **Keep plots and tables legible when space is tight.** Protect data area from optional inspectors with existing collapse, dock, resize and overflow behavior. When controls reflow, keep the primary action and current input visible. Long names retain a readable distinguishing part and full accessible name. Keep scientific values aligned with units, panels visually quiet, and focus and selection distinguishable in both themes. Review the toolbar and worksheet together on a populated wide table at 1024 × 700 and at raised display scaling. Use existing component tokens and responsive layout conventions.
5. **Make keyboard use a first-class route.** Test moving among Library, plot, data, results and tool surfaces with the existing focus cycle. Check visible focus, meaningful control names, arrow navigation where appropriate, and consistent Escape/close behavior with focus returned to the opener. Test disabled reasons, submenu reachability, dialogs, and row selection with a Windows screen reader in addition to browser accessibility snapshots. Keep platform-reserved key chords truthful in browser and desktop labels.
6. **Make busy, error and recoverable states actionable.** For a long import, analysis or export, identify the operation and the relevant input. Show determinate progress where measured, a usable Cancel where supported, and what completed. If anything fails, put recovery beside the affected worksheet, result or job and keep its last valid state visible where safe. Opening a preview should not mutate data. For changes that apply immediately, preserve Undo and show what changed. For staged dialogs, document what Apply, OK and Cancel commit and how pending revisions appear.

### How to tell whether the GUI improved

Use a short task study before and after the first slices. Give participants the task and files, with the commands left for them to discover. Include a new user and users familiar with Origin and JMP. Treat a small convenience sample as directional. Record the viewport, device, baseline build, fixture, starting state, success, time, detours, recovery attempts and any action taken on the wrong object. Capture the final artifacts and verify their contents. This study requires no new in-app telemetry.

| Task | What to measure | Proposed launch target |
| --- | --- | --- |
| New user imports XY data and writes a first editable figure | Unaided completion, time until a meaningful plot, correct X/Y/error roles and ability to find the original source | Establish a baseline first. Target successful unaided completion on the synthetic task, and reduce the median number of detours from baseline. |
| Origin user finds the plotted data, edits a figure and exports it | Whether the user identifies the target, keeps the table and plot visible, and produces the intended vector figure | Zero wrong-target files in the fixture and all test participants able to explain the export destination and source. |
| JMP user compares groups and saves a result + report | Exact method reached, correct categorical roles and observation count, successful report, ability to find the saved result | No silent method substitution. The tested result and exported report agree on input and output. |
| Returning user reopens a project whose source changed | Whether the user recognizes stale output, finds recovery, and preserves the previous result when canceling | Each test participant reaches the right recovery action without guidance. No lost prior result or accidental stale publication in the fixture. |
| Power user uses keyboard and narrow layout | Can complete primary actions and recover focus while viewport size or scale changes | Primary interactions remain reachable at the tested size and scales. No keyboard trap, inaccessible primary action, or hidden current scope in the acceptance script. |

These are proposed acceptance targets, not measured usability results. Keep failure counts by scenario so a pleasant demo cannot hide an export, provenance or recovery problem. Use the real-project replacement gate in the preceding section to check whether the changes hold up in daily work.

**Start with one coherent pilot.** Take the existing XY and grouped fixtures through the proposed experience before rolling it out to every command. Use short interaction sketches or review screenshots from the actual implementation at four points: empty workspace, plot beside source, first result, and export. The first design review should answer which object is active, what the user can do next, and how to undo or recover at each point.
